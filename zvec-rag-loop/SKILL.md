# zvec-rag-loop：知识库检索的工作流

分工：本 Skill 管**检索过程**——查什么、查几轮、够不够、怎么核实。`zvec-rag` 管**结果呈现**——引用格式、`band`/`match_score` 的解读、空结果措辞、回答写法。两份不重复对方内容。

一句话纪律：**先确认快照里有这件事，再解释为什么没查到。**

## 1. 检索前：花一次读文件的时间，省掉五轮盲查

`dsh_kb_search` 只能告诉你「这次没召回」，答不出「为什么」。为什么在磁盘上，读一次就够：

```sh
node <本 Skill 目录>/scripts/kb-inspect.mjs                 # 默认读 ./.dsh-kb-zvec
node <本 Skill 目录>/scripts/kb-inspect.mjs <工作区>/.dsh-kb-zvec --kb kb_xxx_1234
```

输出的每一项都可能改变你的检索策略，读法：

| 看到 | 含义 | 该怎么办 |
|---|---|---|
| `⚠ N 篇不在服务快照里` | 文档上传了但没进索引（`status=pending` / `chunks=待构建`） | 别再换词重试——召不到是必然的。告诉用户去界面构建，或改问已有快照能答的部分 |
| `检索策略 继承部署默认` | 该库没设自己的阈值，用部署的 `minScore`（常见 0.55） | 低于阈值的命中不会出现。你无法从工具放宽，见 §6 |
| `minScore=0.7 …` | 这个库的地板被人为抬高了 | 弱命中被挡不是内容缺失，按 `below_floor` 如实说 |
| `mode=dense` | 全文通路被关，专名精确匹配不再有额外证据 | 裸查一个专有名词更容易空 |
| `切分 … chunk=512` / `分词 jieba` | 一条答案可能被切成两片，各含一半 | 用 §4 的两片拼证，别指望单片含完整论断 |
| `按篇分片合计 ≠ 快照记` | 文档日志与快照不同版次 | 以快照为准，说明「界面显示与索引不同版」 |
| 存储根不存在（exit 2） | 该工作区从未建过知识库 | 见 §2 的工作区隔离 |

脚本只读磁盘、不发检索、不打印正文。构建进行中的库，它读到的仍是上一个已发布快照——这本身就是答案。

## 2. 选库

- `collection` 可省略。省略时：只有一个已构建库就直接查它；多个则工具返回清单（含 id、名称、构建状态），**选一个再调一次**，别凭记忆猜 id（`<domain>_<hex>` 形式猜不中）。
- 用户在对话里 `@` 了某个知识库 → 那是他替你选的，除非明显选错，不要换库。
- **库的边界是工作区**：store root 是 `<会话工作区>/.dsh-kb-zvec`，不是全局。「上次那个库不见了」最常见的原因是会话工作区不同，而不是数据丢了。先在当前工作区确认存储根存在再下结论。
- 归一化分数**不能跨库比较**（各库模型、维度、语料不同）。跨库对照只比命中的原文，不比分数。

## 3. 分解与并行

一次调用只问一件事——这条对多跳问题尤其值钱。

1. 先把问题写成**子命题清单**（要下结论，每条都得有出处）。3 条以下就别铺开流程，直接查。
2. 每个子命题一条查询，**同一轮并行发出**。4 条独立查询胜过 1 条复合查询。
3. 措辞用文档里会出现的词，不用你的抽象概括；专有名词与缩写按原文写法查。
4. 一轮后对账：哪些子命题已有可引用证据，哪些还空着。只对空着的部分换词重试。

## 4. 迭代与停止

- **换词优先于加大 `topk`。** 默认 `topk` 取该库配置的检索策略；显式传 `topk` 上限 50。召回池（`candidates`）在工具里改不动，所以调 `topk` 只改「返回几条」，不改「能找到几条」。
- 需要完整上下文时，用 `read` 打开命中里的 `source_path`——那是**入库时存下的快照正文**，正是切分与索引所依据的那一份。命中片段在工具渲染里被压到 300 字，`char_start`/`char_end` 是这份正文内的字符偏移，`line` 是该片首字符所在行；按行读、按字符区间核对，别把偏移当行号。
- 一条论断的证据可能横跨两片：同 `doc_id` 的相邻 `ordinal` 通常连着。两片互相印证才算读完，只引用其中一片要显式说明另一片的存在。
- **停止条件**（满足任一即停，不要为凑篇幅继续检索）：
  1. 每个待下结论的论断都有一条可回溯命中；
  2. 同一子命题连续两轮换词都无新命中；
  3. 剩余缺口已定位到 §1/§5 的某个成因——此时「说明为什么答不了」就是交付。
- 两库或两文档说法冲突时**报告冲突**，各自给出处；不要静默择一说成定论。

## 5. 核实与失败态定位

下判断前，指得回原文（`zvec-rag` §5 的引用格式）。核实优先读快照正文；原始上传件可能已移动或被改写，与索引不同版次，引用它会造出一个无法被证伪的引用。

召回不足时的成因，按能不能自己修排序：

| 现象 | 成因 | 你能否自己解决 |
|---|---|---|
| 空 + `below_floor` 很大 | 阈值挡的 | 否，见 §6 |
| 空 + `fts_only_hits > 0` | 词精确存在但向量证据弱 | 部分：换更语义化的问法再试一次 |
| 某篇文档怎么查都不出现 | 它没进服务快照 | 否：需用户构建（`kb-inspect` 直接指出是哪几篇） |
| 换个目录就查不到 | 工作区不同，库不同 | 是：确认 cwd 与存储根 |
| 构建报缺嵌入服务 / 检索报无法向量化 | 该部署没配 embedding 端点，或端点不可达 | 否：属部署配置 |
| 界面显示「构建中」 | 检索仍读上一份已发布快照 | 是：等一下再查，或明确告知这是旧快照的答案 |

`timeout` 与 `cancelled` 是两件事（前者预算耗尽，后者调用方撤回），按 `zvec-rag` §6 分别表述。

## 6. 工具改不动的东西，别假装能改

`dsh_kb_search` 只有 `query` / `collection` / `topk` 三个参数。所以：

- 相关性地板（`minScore` 0–1）、候选池（`candidates` 20–1000）、检索模式（`hybrid` / `仅稠密`）、返回条数（`topk` 1–50）——**都在该库的「检索策略」页里**，由人配置；没配过的库继承部署默认。你判断阈值挡了有用证据，就把这个判断连同 `below_floor` 的数字说清楚，请用户去那一页改，而不是连查十遍。
- 召回不够时优先请人抬 `candidates` 而不是 `topk`：前者是「引擎考虑多少条」的上限，后者只是「返回几条」的截断。
- 切分策略与分词器同样在界面里；改它们会让下一次构建全量重建（分词器是建集合时定死的 schema 属性）。这是用户的决定，不是检索时的重试。
- 上传文档、触发构建、看构建进度，都在插件的「知识库」界面里。

## 7. 收尾自检

- [ ] 查过快照是否覆盖（而不是直接开始盲查）？
- [ ] 每个论断有一条命中或快照原文支撑，或已列为缺口？
- [ ] 同一子命题最多两轮就收手了？
- [ ] 冲突与跨版次（快照 vs 原件、日志 vs 索引）如实报告了？
- [ ] 把「改不动的旋钮」推给了对的人，而不是反复重试？
- [ ] 呈现按 `zvec-rag`：引用区、`band`/分数、空结果三种读法？
