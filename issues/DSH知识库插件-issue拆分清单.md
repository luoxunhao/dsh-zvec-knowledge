## 1 拆分原则

1. **每条 issue 对应一条可独立验收的交付链路**，不按「前端/后端」切分——设计规范第 9 章明确界面术语必须与 zvec 实际模型对齐，前后端字段命名强耦合（`query` / `collection` / `topk` / `match_score`），切开会导致契约漂移。
2. **下层只允许使用上层已定义的元素**（沿用文档 2.4 的四层组织：基础 → 组件 → 业务 → 界面）。
3. **设计稿画板是视觉真源，issue 正文只引用章节号与令牌名，不复写色值**——避免清单与规范二次漂移。
4. **待决事项不进入任何 issue 的范围**，统一收敛到第 6 节，由业务侧确认后另开。

## 4 Issue 详情

### KB-01 · 插件工程骨架与 Host/Client 双面契约

| 项 | 内容 |
|----|------|
| 优先级 | P0 |
| 类型 | 基建 |
| 依赖 | 无 |
| 依据 | 设计规范 9.2（插件契约与界面映射）、9.4；`dsh-plugin-development` Skill §3、§6、§7 |

**范围**

- 初始化插件包，声明 `dsh.bundle.patch` 指向 `cordis.patch.yml`；需要 Web 可视化面，因此同时声明 `dsh.client.platform = "web"` 与真实存在的 `exports["./client"]`。
- `cordis.patch.yml` 为顶层数组，用 `insert` 行声明 `id` / `name` / `config`；`config` 是整段替换语义，覆盖时必须重述所需键。
- Host / Client 两个 tsc program 分离，避免同名 Context service 的 declaration merge 冲突；client 走官方 tsdown helper，产物自动包装为 `window.__ModuleLoader__.load`。
- 声明必需注入：host 侧 `tools`（按需追加 persistence / webserver），client 侧 `slots`。`inject` 是必需 service，未满足时 fiber 保持 pending，不得用轮询模拟依赖注入。
- 所有 route / registry / timer / watcher / DOM 归当前 fiber，disposer 顺序为「注销入口 → 等待或取消在途工作 → 关闭资源」。
- 建立 profile 安装与 `--dump-config` 对账的可复现脚本。

**验收标准**

- [x] `pnpm typecheck` 双 program（host / client）均通过。→ 复核：`tsconfig.json`（exclude `src/client`）与 `tsconfig.client.json` 为真正互斥的双 program，`npm run typecheck` exit 0。
- [x] client bundle 纯度门通过，未越过模块表（`@deepseek-ai/dsh-client-runtime/client` 属临时豁免，不得泛化）。→ 复核：`lib/client.js` 仅两处 `require('react')` / `require('react/jsx-runtime')`，均在模块表内；无豁免泛化。
- [x] 插件包 exports、`files` 与产物三者一致，无指向不存在文件的入口。→ 复核：`verify-manifest.mjs` 逐条断言 exports 目标存在、`files` 覆盖 `lib/`+patch、`dsh.client.platform === 'web'`、patch 首内容行为顶层数组；打包产物 13 个文件与声明一致。
- [x] 全新临时 `DSH_HOME` + 新 profile 安装成功并可启动。→ 复核：`kb-tgz` profile 由打包 tarball 安装，`dsh.profile.bundles` 已含 `dsh-zvec-knowledge`，安装成功。
- [ ] `dsh --profile <scratch> --dump-config` 中出现插件层，行 `id` / `name` / `config` 与预期一致。**未过**：`kb-scratch`（`link:` 方式）安装时 `dsh: warning: dsh-zvec-knowledge declares no dsh.bundle — installed as a plain dependency, not a profile layer`，其 `package.json` 的 `bundles` 仍只有 `@deepseek-ai/dsh-base`。唯一「通过」的 `dumpconfig.txt` 存在两处问题：插件层来自 `kb-tgz` 而非 `kb-scratch`，且片段在 `retrieval:` 处截断（无 `topk` / `minScore`）。→ 关闭条件：以 tarball（或已修好的 link: 路径）重跑并把完整 `id`/`name`/`config` 留档，说明是哪个 profile。
- [ ] 建立 profile 安装与 `--dump-config` 对账的可复现脚本。**未过**（范围项）：`package.json.scripts` 无任何 profile / dump-config 入口，现有证据均为手工日志。

**KB-01 结论：部分闭环。** 4/5 验收项通过、1 项范围项缺失；阻塞点是 profile 层装载这一条（`link:` 安装路径不 reconcile bundle 层）。

**不做**：业务界面、令牌定义、zvec 调用。

|----|------|

| 类型 | 基建 |
| 依赖 | KB-01 |

**范围**

### KB-03 · 基础组件库（P0 组件 + 五态覆盖）

| 项 | 内容 |
|----|------|
| 优先级 | P0 |
| 类型 | 组件 |
| 依赖 | KB-02 |
| 依据 | 设计规范 4.1–4.7、9.4（P0 行） |

**范围**

- 按钮四变体（primary / secondary / ghost / danger）与三尺寸（sm 28 / md 34 / lg 40），危险操作必须二次确认。
- 输入类：文本框（含聚焦态主色描边 + 外发光，不用投影表达聚焦）、搜索框、文本域。
- 选择类：下拉选择（超长值截断 + 完整值悬浮提示）、开关（必须附文字说明）、复选框、单选、分段控件。
- 标签（中性 / 品牌 / 可移除）与计数徽标（超两位显示 `99+`，禁止无限增长撑破布局）。
- 状态胶囊：文字 + 实色（或实色圆点）+ 描边三件套**缺一即违规**；表格内可压至 22 并取消圆点，但文字与描边必须保留。
- 图标按钮（34×34）必须有悬浮提示与可访问名称，禁止无文字且无提示的纯图标操作。
- 选项卡：选中态主色文字 + 2px 主色下划线。

**验收标准**

- [ ] 每个组件实现 default / hover / focus / disabled / loading 五态，缺一视为未完成。**未过**：门禁 `INTERACTIVE_STATES` 只校验 hover / focus / disabled / loading **四**态（default 无法机械校验，尚可接受），但另有 4/12 个样式表经自造分层豁免：`StatusPill` / `Tag` / `CountBadge` 记为 marker、`Spinner` 记为 indicator，而规范原文是「每个组件」，未授权分层。`Spinner.module.css` 既无 `loading` 也无 `aria-busy`。→ 关闭条件：把 marker/indicator 分层写回规范取得授权，或补齐这 4 个组件的状态集。
- [ ] focus 必须可见且未被移除轮廓；disabled 可被读屏识别为不可用；loading 保持尺寸稳定、无布局跳动。**部分过**：focus 可见（`base.css` `.kb-root :focus-visible`，用 `--kb-shadow-focus` 外发光而非投影，符合范围要求）✓；disabled 用原生 `disabled` 属性、可被读屏识别 ✓；loading 尺寸稳定仅有 `.loading { cursor: progress }` 之类的实现，**无任何门禁断言**，需随 KB-05+ 真实界面复核。
- [ ] 状态胶囊在灰度与色觉障碍模拟下仍可区分。**未过（实色规则被违反）**：规范要求「文字 + 实色（或实色圆点）+ 描边」。实际 `StatusPill.module.css:41-69` 的 `background` 用的是 `-bg` **浅底**令牌（如 `--kb-status-ready-bg` = `#0F2E2B`），不是实色；唯一的实色来自 `.dot { background: currentColor }`（`:37`），而 `.dense`（表格内形态）在 `StatusPill.tsx:38` **移除圆点**却保留浅底——即密集态是「文字 + 浅底 + 描边」，全程无实色。同时 `--kb-status-ready`（`#2FB3A4`，规范 `successReady`）等实色令牌已定义却**零引用**。→ 关闭条件：密集态保留实色承载（实色点或实色描边），或改用实色底 + 反白文字。注：文字 + 描边俱在，故「不靠颜色单独承载」本身仍成立，色觉模拟可区分性大概率不受影响，但「实色」这一条字面未满足。
- [ ] 全页 primary 按钮唯一性可被校验（组件层给出用法约束）。**偏弱**：`Button.tsx:60-86` 用**模块级全局**计数器统计已挂载 primary，`console.warn` 且仅 dev 生效；既非「每页」口径，也不可能失败。→ 关闭条件：改为可按视图作用域校验（或明确接受 warn 级约束并回写规范）。
- [ ] 负向校验必须说明原因，不允许只提示「输入有误」。**偏弱**：`TextField` 要求传 `error`，但 `invalid` 缺 `error` 时仅 `console.warn`，不阻断。需随 KB-06 真实表单复核。

**范围项偏差（不进验收清单但需记录）**：

### KB-10 · zvec 进程内集成与持久化

  **修正**：引擎无 PQ，量化器取 `INT8`（见 9.1 与第 9 节 #2）。
- 混合检索管道：稠密向量 + 全文检索（BM25 / n-gram），融合方式固定 RRF。
  **修正**：融合由引擎 `multiQuerySync` + `rerank: { type: 'rrf' }` 完成，不手写；RRF 分是排名分、不等于 `match_score`（见 9.1 #9）。
- 持久化：路径显式配置且按 workspace 隔离，**禁止用 `process.cwd()` 默认值散落用户数据**；同一资源读改写串行化；并发创建采用 no-clobber 语义；人可读 JSON 用同目录临时文件 + fsync + 原子发布；追加日志处理 torn tail。
- 恢复与 HMR 不假设创建事件会重放，必要时显式扫描并回填已有对象。
- 构建长任务归当前 fiber 所有，暴露进度、取消与失败重试，且资源可清理。

**验收标准**（复核证据：`npm run verify:kb10`，53 项全绿）

- [x] 临时目录中的文件往返、锁、归档与恢复测试通过。→ 原子写往返、`withFileLock` 串行化（同键排队、异键并发、拒绝不污染链）、JSONL 完整读 / torn tail 丢弃 / 中段损坏抛错、重命名与删除，均已断言。
- [x] 并发创建同一 Collection 不互相覆盖（no-clobber 可验证）。→ 三路并发创建仅一路成功（1/3），且落盘记录与胜者一致；存在性检查 + 引擎拒绝双保险。
- [x] 进程被强制终止后索引可恢复到一致状态，无半写文件。→ 真实子进程写入中被 `taskkill /F /T` 强杀，之后集合可重开、重建成功。理由：写入目标恒为非活动槽，读者不可达，故无需回滚。
- [x] 插件卸载后无残留 timer / watcher / 文件句柄 / socket。→ `apply()` 注册 fiber disposer，卸载时 `disposeAll()` 关闭全部池化句柄；测试断言释放后计数归零且目录可重新打开（证明引擎独占锁已释放）。无 timer / watcher / socket。
- [x] 存储路径在不同 workspace 下物理隔离，可给出路径证据。→ 测试输出两个 workspace 的绝对根路径对比，并断言集合只在所属 workspace 可见；绝对 `stateDir` 作为显式豁免被尊重；`../escape` 类越权路径被拒。
- [x] 出参 `match_score` 为归一化分数（0–1），原始向量距离不出现在任何接口与界面。→ `toMatchScore = clamp(1 - distance)`；测试断言所有命中分数落在 [0,1]、命中对象**不含** `score` / `distance` 字段、分档与 §3.4 一致。

- 双槽位快照（`store/snapshot.ts`）：重建期间旧索引持续可服务，发布为一次原子指针翻转，收敛了 KB-07「重建返回上一次快照」的硬要求。

- 切分器（`store/chunk.ts`）：三种模式、token 估算、代码块保护、最小分片丢弃、预览汇总。

**KB-10 结论：闭环。** 6/6 验收项通过，53 项自动化断言可复跑。

1. 颜色不兼职：品牌色只承担主操作、选中态与焦点态；语义色只承担状态表达。

## 9 zvec 实测偏差（首次实施后回补，影响 KB-07 / KB-08 / KB-10）

在 `plugin/` 的首次实现中真机验证了 `@zvec/zvec` 0.7.1（win32-x64 绑定），发现设计规范的三处技术假设
与实际 API 不符。下列 issue 的验收标准需相应修正，否则实现会照着一个不存在的量化器和一个方向相反的
分数语义去写。

| # | 规范假设 | 实测结论 | 影响的 issue | 处置 |
|---|----------|----------|--------------|------|
| 1 | 命中分数由 zvec 距离归一化得到（§3.4 表述正确） | `querySync` 返回的 `score` 是**距离**（越小越相似），列表已按距离升序；查询向量等于某文档得 0，正交得 1 | KB-08、KB-09 | 规范化必须实现为 `matchScore = clamp(1 - distance)`，而非对原值 clamp。方向读反会把最差命中排在最前，并让全部命中越过 0.55 阈值 |
| 2 | 量化器「PQ-INT8（压缩 4×）」 | `ZVecQuantizeType` 只有 `FP16 / INT8 / INT4`，**不存在 PQ**；另有 RaBitQ 索引族 `HNSW_RABITQ` / `IVF_RABITQ` | KB-07 | 配置器选项与默认值改为 `INT8`；「压缩 4×」对应 FP32→INT8 的 4 倍压缩。若要用 RaBitQ，它属于索引类型而非量化器，UI 归属需重新划分 |
| 3 | 索引类型 HNSW / IVF / DiskANN | `ZVecIndexType` 实际含 `HNSW` / `IVF` / `FLAT` / `HNSW_RABITQ` / `DISKANN` / `IVF_RABITQ` / `INVERT` / `FTS` | KB-07 | 分段控件至少覆盖 HNSW / IVF / DiskANN；两个 RaBitQ 变体是否对用户暴露待业务确认 |
| 4 | 距离度量默认 cosine（§5.6） | HNSW / IVF / DiskANN / FLAT 的 `metricType` **默认值均为 IP（内积）** | KB-07、KB-10 | 必须按索引显式设置 `COSINE`，否则分数尺度与 0.55 阈值全部失准 |
| 5 | 集合可反复按建库方式打开 | `ZVecCreateAndOpen(path, schema)` 要求 `path` **不存在**；重开既有集合必须走 `ZVecOpen(path)`，且不接收 schema | KB-05、KB-10 | 集合打开分两条路径（新建 / 重开），实现需按存在性分派；schema 随集合持久化，不随打开传入 |

**已验证可用**：原生绑定在 Windows x86_64 上加载正常，HNSW + COSINE + `m=32` / `efConstruction=200`
被接受，写入、检索、关闭后重开数据一致，四档置信度映射（1.0 / 0.994 / 0.707 / 0）与余弦理论值吻合。
证据留档：`plugin/zvec-smoke-report.json`，可复跑命令 `npm run smoke:zvec`。

### 9.1 KB-10 实施期新增实测结论（影响 KB-05 / KB-07 / KB-08 / KB-09）

补充探测证据：`plugin/scripts/zvec-probe10.mjs`、`zvec-probe-filter.mjs`、`zvec-probe-lock.mjs`，
以及验收套件 `plugin/scripts/verify-kb10.mjs`（53 项，`npm run verify:kb10`）。

| # | 假设 / 直觉 | 实测结论 | 影响的 issue | 处置 |
|---|-------------|----------|--------------|------|
| 6 | 「路径已存在」会报 `ZVEC_ALREADY_EXISTS` | `ZVecCreateAndOpen` 对已存在路径抛 **`ZVEC_INVALID_ARGUMENT`**（消息为 `path validate failed: path[...] exists`），与「参数非法」同码 | KB-05、KB-10 | **不能靠错误码分派新建 / 重开**，必须按路径存在性判断。已按此实现（`store/snapshot.ts`） |
| 7 | 同一集合可被多次打开（含只读并发读） | 集合目录带**独占锁**：同一路径第二次 `ZVecOpen` 无论读写都失败（`ZVEC_INTERNAL_ERROR: Can't lock .../LOCK`）；关闭后可重开 | KB-08、KB-10 | 必须**按槽位池化句柄**并引用计数，不能按请求开闭。已实现 `store/registry.ts`；插件卸载 disposer 释放全部句柄，否则重载会撞锁 |
| 8 | 标量过滤用 SQL 风格 `==` | 过滤语言只接受**单等号 `=`**，`==` 直接语法报错；字符串用单引号，支持 `LIKE` / `IN` / `AND` / `BETWEEN`；`SELECT ... WHERE` 不被接受 | KB-06、KB-08 | 过滤表达式统一由 `documentFilter()` 生成并转义引号，禁止在别处手写 |
| 9 | 全文检索需自己实现融合 | 引擎自带 **FTS 索引**（`tokenizerName` 支持 `standard` / `ngram` / `jieba` / `whitespace`）与 **`multiQuerySync` + `rerank: { type: 'rrf' }`**；中文 `matchString: '检索'` 实测命中 | KB-07、KB-08 | 混合检索直接用引擎融合，不手写 RRF。**注意**：RRF 返回的是**排名融合分**（量纲取决于 `rankConstant`），不是相似度，不能当 `match_score` 用；已改为「保留融合排序 + 取该命中自身稠密距离归一化」 |
| 10 | 重建索引期间旧索引仍可读 | 引擎不支持同目录双开，故「旧快照继续服务」必须由**双槽位 + 指针切换**实现：写入非活动槽，发布时原子翻转 `meta.json` 的 `active` | KB-07、KB-10 | 已实现（`store/snapshot.ts`）。取消或失败只丢弃非活动槽，检索始终读活动槽，天然满足「重建中返回上一次快照」 |

**结论**：第 9 条推翻了「自己算 RRF 分数即可」的直觉，第 7 条推翻了「按请求开集合」的直觉——
两者都会在并发一上来时以锁错误或错误排序暴露，已在 KB-10 层一次性收口，KB-07 / KB-08 直接复用。
