### 1.2 由此导出的「合格解析器」判据（可直接进门禁）

给定一篇含标题、含表、含代码的样例文档，解析产物 `text` 必须满足：

1. `/(?:^|\n)#{1,6} \S/` 命中数 ≥ 样例文档中的标题数（结构保持）；
2. 存在至少一处 `/^\|.*\|\s*$/` 行，且其后一行匹配 `/^\|[\s:|-]+\|\s*$/`（表头 + 分隔行，C2）；
3. 存在成对的 ``` 或 `~~~` 围栏（C3）；
4. `text` 中不出现 `\r`（C4）；
5. 不产结构化时（如未打标签的 PDF），必须返回可判定的降级标记，门禁断言该标记为 `flat-text`（C12）。

这五条同时是 §6 各阶段验收门禁的核心断言。

### 4.0 总览

### 4.1 共享主干：HTML → Markdown

选择 unified 直用组合而非 `turndown`，理由只有一条但决定性：**它的默认值就是切分器要读的东西**（ATX + 强制围栏 [R45]），因此「忘记配置」不会造成静默降级；而 `turndown` 的三个默认值全反 [R50]。这条主干同时服务 `html` 直传与 `docx`（经 mammoth 的 HTML 出口 [R18]），是一份实现、一份测试。

必须显式做的四件事（都可进门禁）：
1. 注册 `mdast-util-gfm-table` 扩展，否则表格节点被丢弃 [R45][R46]；
2. 把 `mdast-util-to-markdown` 的 `setext` 显式钉为 `false`（防上游改默认）；
3. 清洗 `href`：丢弃 `javascript:` / `data:` 目标（mammoth README 明文告警 [R18]）；
4. 产物行尾统一 `\n`（C4）。

### 4.2 DOCX

`mammoth` 的默认映射同时按 `w:styleId`（默认表前六条是 class 选择器 `p.Heading1 => h1:fresh`，
`options-reader.js:6-11`）与 `w:name` 命中，因此**中文显示名本身不会让标题消失**——「英文 styleId + 名字为『标题 1』」实测得到 `<h1>`（§10.1 用例 C）。
真正会整篇静默丢标题的是 **styleId 不是 `Heading<N>`、且名字也不是英文规范名**的那一类（多为非 Word 生成器产出，实测用例 D 得到 `<p>`），
外加 Word 用「目录级别」（`w:outlineLvl`）标标题而样式名自定义的情形——mammoth 完全不读 `outlineLvl`。
两者都由 §10.3 的推导式映射解决，不靠硬编码中英两份 `styleMap`。图片必须显式处理：默认内联 base64 [R18] 会把百 KB 到数 MB 的不透明串塞进 `documents.jsonl`，既污染向量也吃掉配额（配额按 `原文字节 + 文本字节` 计算，`operations.ts:638-643`）。推荐 `convertImage: () => ({src: '', alt: ...})` 式丢弃 + 在产物里留一行 `![图片]` 占位，语义与体量都可控（本仓库真机样本无图片，该路径未复现，留待阶段 2 用含图 fixture 定，§10.4）。

### 4.3 PDF（本方案里唯一需要自研结构推断的格式）

事实基线：`pdfjs-dist@6.3.289` 的 `getTextContent` 只给 `TextItem` 列表（带位置矩阵与 `hasEOL`）和可选的标记内容事件，**官方类型声明未承诺 items 的顺序，也未承诺任何标题语义** [R4]。因此「PDF → 带层级 Markdown」没有开箱即用的纯 JS 方案，必须自己实现三段：

1. **行重建**：按 `transform` 的 y 分量分行、x 分量排序，`hasEOL` 作辅助（多栏文档不能只靠流顺序）；
2. **结构优先**：`includeMarkedContent: true` 时，tagged PDF 的结构标签若映射到 `H1..H6` / `P` / `Table` / `L` / `Code`，直接落成 ATX 标题、管道表、列表、围栏。标签名所在字段 **未验证**（§7 U1）→ 阶段 3 的第一个动作就是在真实 fixture 上打印 items 确认；
3. **字号聚类兜底**：无标签时按 `height`/`fontName` 聚类，把显著大于正文众数的行判为标题并按出现深度分配 `#` 层级；表格按「同一 y 上多个 x 簇 + 行间对齐」判据合成管道表。所有推断产物一律记 `structure: 'inferred'`（区别于 `tagged`），不可当原文标题使用。

CJK：必须把 `cMapUrl` / `standardFontDataUrl` / `wasmUrl` 指向包内本地目录（`cmaps/`、`standard_fonts/`、`wasm/` 均随包 [R2]；本机实测 `cmaps/` 169 条目 / 1.5 MB，见 §11.3），这同时满足 C7（无外网）；`cMapPacked` 默认 `true` [R4]。**路径形态在 Windows 上有两种要求，写成一个 helper 必错一边：`workerSrc` 要 `file://` URL，`cMapUrl`/`standardFontDataUrl` 要正斜杠绝对路径带尾斜杠（详见 §11.4 两条陷阱）。** 加密 PDF：pdfjs 需要密码，`getDocument` 的口令选项与错误形态 **未验证**（§7 U7）→ 阶段 3 用一份真加密 fixture 定死错误文案。

### 4.4 XLSX / CSV

两者共用一个 `rowsToMarkdownTable(rows)`：首行当表头、生成 `|---|` 分隔行、单元格内的 `|` 与换行转义、每表前置 `## <sheet/文件名>` 标题（给 heading 模式一个可检索的锚）。XLSX 用 `read-excel-file`（MIT、活跃、零安装脚本、纯 JS 依赖 [R27][R28]）。**不使用 npm 上的 `xlsx`**：0.18.5 是注册表最新版且无修补版本 [R29][R36]。

### 4.5 JSON

本地函数，见 §2.5。

### 4.6 扫描件与 OCR 的诚实降级

上传期对 PDF 做一次**廉价预检**（只打开文档、取第 1 页文本、统计字符数与页数，不解析全文）：
- 文本运行数 ≈ 0 且页数 > 0 → 判为「无文本层（扫描件）」，**上传即拒**，remedy 保持现有语义并升级：`PDF 无文本层（扫描件或图片型）。本插件不含 OCR；请先用离线 OCR 转成带文本层的 PDF 或 Markdown 后上传`；
- 打不开/需要口令 → `PDF 无法打开或需要口令。请导出去除权限口令的副本后上传`；
- 有文本层 → 接受，构建期解析，若最终产物未过 §1.2 判据则 `structure: 'flat-text'` 并如实上报。

这样 §C11（广告过的格式必须上传时给可执行答复）与「不引入 OCR 依赖」同时成立，且 `strategy-evidence` 面板本来就是「本文档未涉及」的语义载体 [R70]，不需要新增 UI 概念。

### 4.7 可选外部适配器（形状，而非具体命令）

- 配置字段（cordis.yml，按仓库「部署可变项必须是校验过的 Config 字段」的约定）：命令 argv 模板数组 + 允许的扩展名白名单 + 超时 + 输出字节上限。**不经 shell**，模板里只有 `{input}` / `{output}` 占位；
- 默认关闭；未配置时该格式走 §4.6/现有 remedy；
- 探测放在**使用时**而非加载时（插件加载期不应 spawn），失败信息点名「未找到已配置的解析命令 X，见 README 的解析器适配器一节」；
- 适配器产物同样过 §1.2 判据，未过则记 `flat-text`；
- 这条路线让 `epub`/`rtf`/`pptx`/`.doc`/`xlsx` 高级格式在不污染默认安装的前提下成为可能。

### 4.8 落到 `ExtractionKind`

现状是 `'verbatim' | 'needs-conversion' | 'unsupported'` 三值 [R60]。建议**不新增第四个 kind**，而是把 kind 的语义收窄为「字节到文本的处理方式」，把「结构保真度」作为正交维度：

```ts
/** How a format is turned into indexable text. */
export type ExtractionKind =
  | 'verbatim'    // 字节即文本，解码即用（现状）
  | 'converted'   // 新：进程内解析器在构建期把原件转成 Markdown
  | 'needs-conversion'
  | 'unsupported'

/** How much document structure survived the conversion. */
export type StructureLevel = 'structured' | 'inferred' | 'flat-text'

export interface ExtractionSupport {
  kind: ExtractionKind
  /** Which converter handles it when kind is 'converted'. */
  converter?: 'html' | 'docx' | 'pdf' | 'xlsx' | 'csv' | 'json'
  /** Upload-time probe that can refuse before a record is written (PDF only today). */
  preflight?: (file: string) => { ok: true } | { ok: false; remedy: string }
  remedy?: string
}
```

理由：`needs-conversion` 现有文案已经承担「教用户怎么做」的职责 [R60]，若再造一个 `converted-degraded` 之类的 kind，`operations.ts:591-596` 的上传判定会从「是不是 verbatim」变成枚举组合测试，而真正需要区分的是**产物有没有结构**——那是一次解析之后的事实，不是格式的先验属性。`StructureLevel` 与 `DocumentRecord` 一起持久化（§5.2），既给 UI/面板读，也给 `strategy-evidence` 的 `applicable` 判定读 [R70]。

`remedy` 文案的写法要求（保持现有约定：说清可接受范围 + 可执行动作）：
- 未配置适配器且解析器失败：`DOCX 解析失败（<原因>）。原件已保留，可在修复后用「重新解析」重试，或先用 pandoc/Word 导出为 Markdown 后上传`；
- `needs-conversion` 只剩真正无解的入口（如 `.doc`、`epub`、扫描 PDF），文案必须区分「本插件不做」与「你需要先做什么」。

## 5 接入设计

### 5.1 上传时解析 vs 构建时解析

**结论：原件写入 + 廉价预检留在上传时；真正的解析移到构建流水线的 parse 阶段。**

| 判据 | 上传时解析 | 构建时解析 |
|---|---|---|
| 事件循环 | 32 MiB PDF 的全文抽取是 CPU 密集，进程内插件（C8）会把整段计算压在宿主循环上；pdfjs 无 worker 时明文退回主线程 “fake worker” [R4] | 已按批次让位的 async 流水线，天然可分文档/分页 yield |
| 进度与取消 | 上传进度是**字节传输**进度，与解析无关；客户端已把两者分成两个轴 [R71] | 流水线本就有 `parse/chunk/index/publish` 四阶段、阶段名与 `cancel()` [R72]，且 `parse` 阶段目前只是空文本过滤 [R72] —— 它就是为这件事留的位 |
| 失败归属 | 抛错即上传失败，用户看不到 `status='failed'` 与 `error` 行 | 每篇一个 `failed` + `error`，其余文档继续 |
| 快速反馈（C11） | 扫描 PDF 立刻被拒 | 靠 §4.6 的上传期预检保住：贵的一律不预检，只判「有没有文本层 / 能不能打开」 |
| 配额记账 | 上传即可算出派生文本字节（现状 `operations.ts:638-643`） | 需两段式（§5.2） |
| 重算（C9） | 派生文本一次写定 | 与 C9 同构：`sources/` 存原件正是为了「以后加了转换器可全库重跑」[R60] |

**异步形态**：解析器调用 `await` + 协作让位，而不是 `worker_threads`。理由：不引入新的生命周期与句柄所有权，且 `build.ts` 已经有 `raceAbort` 的取消骨架 [R72]；PDF 侧逐页 `await page.getTextContent()` 本身就是可中断的异步序列。若实测（§6 阶段 3）证明单个 32 MiB PDF 的解析仍会长时间独占循环，则把解析挪进 `worker_threads`，并把「worker 内不得触碰 zvec 句柄」写死为约束——这一步由门禁 §6.3 的独占时长断言决定，不预先付复杂度。

### 5.2 数据结构改动（最小集）

| 位置 | 改动 | 为什么必须 |
|---|---|---|
| `DocumentRecord` | 新增可选 `structure?: StructureLevel`、`parsedAt?: string`、`converter?: 'verbatim' \| 'html' \| ... \| 'external'`；`text` 允许 `''`（类型上仍是 `string`） | 未解析 ≠ 空文档；`chunks: null` 已经在区分「未测量」与 0 [R73]，同一思路要求 `text: ''` 只表示「还没解析」，不能表示「解析出 0 字」——后者要由 `failed` + `error` 表达 |
| `documents.jsonl` | 解析成功后回填 `text` / `structure` / `parsedAt` | 走现成的 `patchDocument`（读-改-写整日志，注释里已说明日志是 append-only + 小体量）[R73] |
| 配额 | 上传期按 `原件字节` 记账（派生文本尚未产生），解析回填时按真实文本字节二次 `admit`；不足则该篇 `failed: 存储配额不足（解析后需要 N）` | 现状 footprint = 原件 + 解码文本 [R74]；移到构建期后必须保住「不超额提交」这条性质 |
| `validateUpload` / `ACCEPTED_EXTENSIONS` | 三处清单（`documents.ts:74`、`DocumentsPage.tsx:32`、`extract.ts` 的 `SUPPORT` 键集）必须同源 | 现状已是复制品；新格式进入时最容易只改一处，门禁需断言三者一致 |
| 增量构建资格 | 把「`structure` 或 converter 版本变化」并入 `incrementalViability` 的强制全量理由 | 现有增量判定已按 chunking/index/tokenizer 变更回退全量 [R75]；换解析器同样是索引内容变更，不回退就会留下新旧混排的语料 |

### 5.3 parse 阶段的实现形状与失败映射

在 `build.ts` 的 `enter('parse')` 与 `enter('chunk')` 之间插入**逐文档解析**，保持既有 `documents` 入参兼容：`DocumentBuildRequest` 增可选 `source?: {file: string, converter: ConverterId, reparse: boolean}`；不带 `source` 的调用（含现有 `verify-build-job` 系门禁）走 `text` 直用，行为不变。

```
enter('parse')
  total = request.documents.length          // 先按「篇」报进度，不再等切完才知道总量
  for each doc:
    if (aborted) return cancelled(...)
    text = doc.source ? await convert(doc.source) : doc.text
    structure = gradeMarkdown(text)          // §1.2 五条判据的可执行版本
    patchDocument(... {text, structure, parsedAt, converter, status: 'building'})
    onProgress(...)                          // 每篇一次，跨过 PROGRESS_INTERVAL 的既有节流语义
    await yieldToEventLoop()
  documents = kept.filter(text.trim() !== '')
```

| 情况 | `status` | `error` | `text` / `structure` | 门禁 |
|---|---|---|---|---|
| 正常 | 继续到 `ready` | — | 全文 / `structured` | 判据 1–4 |
| 结构不可恢复（无标签 PDF、纯段落 docx） | `ready` | — | 全文 / `flat-text` | 面板 `applicable: false` 语义 [R70] |
| 解析器抛错 | `failed` | 抛错信息 + 建议动作 | `''` | 单篇失败不得终止整场构建 |
| 加密 / 需口令 PDF | 上传期即拒（不落 `failed`） | 预检 remedy | — | §4.6 |
| 无文本层（扫描件） | 上传期即拒 | OCR remedy | — | §4.6 |
| 解析成功但 `trim() === ''` | `failed` | `解析后无文本内容（可能是纯图片页或空表）` | `''` | 与现有 `addDocument` 的同名文案保持一致 [R74] |
| 产物超上限（如 `MAX_PARSED_CHARS`） | `ready` | — | 截断 + `truncated: true`，日志一行 | 截断必须可见 |
| 构建被取消于 parse 中 | 回到 `pending`（当前 `building` 的复位） | — | 保留上次值 | 现有取消语义：丢弃槽、检索继续读旧快照 [R72] |

**关键不变量**：单篇解析失败绝不使整场构建 `ok: false`。现有实现在 `try` 里抛错就丢弃槽并整体失败 [R72]，因此 parse 阶段的每篇解析必须包在自己的 `try/catch` 内并把失败记到文档上；只有系统性错误（存储不可写、配额）才让构建整体失败。

### 5.4 CPU / 内存边界

| 边界 | 值（建议，作为可校验 Config 字段而非 `DEFAULT_*` 常量） | 依据 |
|---|---|---|
| 单文档解析墙钟 | `PARSE_TIMEOUT_MS`（默认 60 s），超时 → 该篇 `failed`，并让位给下一批 | mammoth 明文自述恶意文档可致「病态性能」的高 CPU/内存 [R18]，不能假定第三方解析器有界 |
| PDF 页数 | `PARSE_MAX_PAGES`（默认 2 000） | 逐页循环可中断；无上限时 32 MiB 的扫描件型大部头会独占循环 |
| 派生文本字节 | `PARSE_MAX_TEXT_BYTES`（默认与 `MAX_UPLOAD_BYTES` 同量级） | 配额与 `documents.jsonl` 的行体量；base64 图片是最容易击穿这条的（§4.2） |
| HTML DOM 规模 | 按输入字节 + 节点数双限 | mammoth/pdfjs 之外，真实世界 HTML 的展开型嵌套同样能撑爆 parse5 |
| ZIP 解压 | DOCX/XLSX 解压后上限（zip-bomb） | mammoth 自述「不做任何净化」[R18]；jszip/fflate 都不给解压比保证 |
| 取消检查 | 每篇、PDF 每页 | `build.ts` 的 `controller.signal` 与 `raceAbort` 已具备，缺的是 parse 内部的检查点 [R72] |

### 5.5 与构建阶段进度上报的衔接

- `BuildProgress.total` 的语义会变：现状 `total` 在切分完成后才被赋值为**分片数**（注释明确「Zero until the parse stage has measured」[R72]），新设计下 parse 阶段先按**篇数**推进 `processed/total`，切分阶段完成后重新按分片数标定。必须保证 `fraction` 单调不回退，否则进度条倒退会被当成构建抖动；
- `STAGE_LABELS.parse = '解析文档'` [R72] 已名实相符，无需改文案；
- 日志：每篇降级/失败各一行，`level` 用 `info`（降级）/ `error`（失败），末尾汇总 `解析 N 篇，其中 M 篇无结构、K 篇失败`——满足 spec 对阶段名与可解释日志的要求 [R72]。

## 6 分阶段落地顺序与验收门禁

门禁一律按 `plugin/scripts/verify-*.mjs` 现有风格：真实临时目录 + 真实库绑定、`check(name, ok, detail)` 双列记账、`rmSync/mkdirSync` 自建 `plugin/tmp/kbXX-*` 现场、**从 `lib/` 导入构建产物**（`verify-upload.mjs` 即 `await import('../lib/host/operations.js')` [R76]）、无外网无 key、fixtures 提交进仓库。新增命令一律挂进 `package.json` 的 `verify` 串行链。

### 阶段 0 —— 判据与 fixtures（不改产品行为）

产出 `src/store/markdown-grade.ts`（§1.2 五条判据的可执行实现）与 fixtures 目录。

| 门禁 | 断言 |
|---|---|
| `verify-parse-grade.mjs` | 判据自身：对「ATX 标题 + 管道表（表头行与分隔行）+ 三反引号 ts 围栏」的组合样例判 `structured`；对纯段落判 `flat-text`；对 setext 标题、缩进代码、缺分隔行的表分别判**不合格**（前两条正是 turndown 的默认产物 [R50]，用它当负向样本）；CRLF 输入被判 `flat-text` |
| — | 负向自证：把判据的 heading 正则改成 `^#{1,6}\s*$` 必须红（防判据写成永真） |

**fixtures 来源**（必须先定，否则后面每一步都在补证据）：

2. HTML/CSV/JSON 直接以文本提交（含中文样例、多栏样例、含公式的表、引号内换行的 CSV）；
3. 任何取自第三方的 PDF fixture 必须在 `fixtures/SOURCES.md` 记录来源 URL 与许可证；本轮**未发现**许可证明确且适合当中文 tagged-PDF 样例的公开语料（§7 U8）。

### 阶段 1 —— CSV / JSON / HTML（零许可风险、零原生、零下载）

| 门禁 | 断言 |

### 阶段 2 —— DOCX

| 门禁 | 断言 |

### 9.2 需要更正的两处

**（a）§5.3 的「每篇 `patchDocument` 回填」会变成 O(N²) 全日志重写。** `patchDocument` 的实现是 `listDocuments` → 改一条 → `replaceDocuments`，而 `replaceDocuments` 把**每条记录连同 `text` 一起 `JSON.stringify` 并整文件原子重写**（`documents.ts:238-251,221`）。`operations.ts:1513-1522` 的注释自己就把这件事写明为「read-modify-write over the whole log」。现状是一次构建只在发布后重写一次；把回填放进 parse 循环，就等于每解析一篇重写一遍全库正文——21 篇 / 2.3 MB 的当前语料是 21 次 2.3 MB 序列化，PDF 量级下会难看得多。

改法二选一，与下面 N1 一起考虑更划算：

1. parse 循环内只把结果留在内存，循环结束后**一次性** `replaceDocuments`（保持「整场构建一次重写」的既有性质）；构建中途崩溃时 `text` 留在旧值，由下一次构建重解析——这与 `chunks: null` 表达「未测量」的既有取向一致；
2. 派生正文不再进 `documents.jsonl`（见 N1），日志只留元数据，回填变成每篇一行的定长写。

**（b）C3 的表述要收紧。** 切分器的围栏保护认 ``` 与 `~~~`（`chunk.ts:280`），但证据面板的 `fenceCount` 只数行首三反引号（`strategy-evidence.ts:141`，`/^```/gm`）。也就是说解析器若输出 `~~~`，切分阶段认它是代码、面板却报「本文档未涉及」。因此对解析器的要求是**只输出三反引号围栏**（`mdast-util-to-markdown` 的 `fence` 默认就是反引号 [R45]，别去改它），并且这条不对称本身值得顺手修掉或进门禁断言，否则它会被当成解析器的错。

### 9.3 §1–§8 漏掉的三条约束

**N1 每次检索都会重读全部派生正文。** `operations.ts:1143` 在 `search()` 里 `new Map(listDocuments(root, collectionId)...)`，而 `listDocuments` 走 `readJsonl` 把每条记录的 `text` 都 `JSON.parse` 出来。实测本仓库现存的 21 篇 Markdown 语料：`documents.jsonl` 2.31 MB、派生正文 166.6 万字符，单次逐行解析 **5.0 ms**；把同一份日志放大 10 倍（2 306 万字节，正是一般 PDF 语料的量级）模拟，单次 **76.5 ms** [R83]。也就是说「每次检索 O(语料正文)」的读放大已经存在，只是现在被 Markdown 语料压在一个可接受的常数里；把 PDF/DOCX 接进来会直接把系数乘上去，且同一份读还发生在 `listCollections`、`listDocuments`、`readCitation` 等每条路径上。

这条对方案的含义比「性能优化」更硬：**派生正文应当从 `documents.jsonl` 移出去**，按篇存成 `sources/doc_<hash>.parsed.md`，日志只留 `id/name/bytes/ext/status/chunks/uploadedAt/builtAt/error/structure/converter/parsedAt` 这类定长元数据。收益是三份的：检索期不再解析正文（N1）、解析回填变成单文件写（9.2a）、并且顺带解决 N2。代价是要一次性的存储布局迁移（`meta.json` 加版本字段，或按「文件是否存在」回落到读 `text` 的旧路径）。

**N2 `source_path` 指向原件，`line`/`char_*` 却按派生正文计算。** `relativeSourcePath` 用 `sourcePath(root, collectionId, record.id, record.ext)`（`operations.ts:1193-1201`），扩展名取的是**上传原件**；而命中里的 `line` 由 `lineOf(record.text, hit.charStart)` 得出（`operations.ts:1171`），`readCitation` 读的也是 `record.text`（`operations.ts:1249` 起）。今天 `md`/`txt` 的原件与派生正文逐字节相同，所以两者恰好一致、问题不可见；一旦允许 PDF/DOCX，「打开 `.doc_18baa879.pdf` 的第 212 行」就是假指引——模型侧引用的可回溯性、KB-13 的可点击原文、以及 `zvec-rag`/`zvec-rag-loop` 两份 skill 里「用 read 打开 source_path 读上下文」这条动作会同时失真。修法与 N1 同一条：`converted` 格式的 `source_path` 指向那份 `.parsed.md`，并在界面上说明「标的是入库正文，不是原始上传件」（这条语义 README 的 KB-13 一节已经写了，只是路径还没跟上）。

**N3 worker 化不是全新设计，且体量决策应该单独摆出来。** §5.1 先按「协作让位 + 门禁实测独占时长」推进、由 §6 阶段 3 的断言决定是否升级 `worker_threads`，这个顺序合理；真要升级时宿主侧已有先例可参照（harness 的 workflow 能力就是 worker-thread provider），不必从零设计生命周期。

体量方面 §6 只标注了阶段 3「唯一引入新体量依赖」，建议再明确一点：阶段 1 与阶段 2 的**全部新增依赖都是小体量纯 JS**（`mammoth` 解压 2.18 MB [R17]，unified 系为数十个小编辑单元包，`read-excel-file`/`papaparse` 均在 MB 以下），只有 `pdfjs-dist` 一项 33 MB / 554 文件、约为本包现有运行时依赖总量的数十倍 [R1][R80]。因此「PDF 要不要跟 HTML/DOCX/CSV/JSON 同一次发布」是一个独立的产品决策：可以拆成可选的第二包（或可选配置项，缺席时 PDF 继续走 §4.6 的 remedy 拒绝），让前四种格式先落地。U1/U2/U8 三条未决也顺势变成这个决策的证据——尤其 U1（tagged PDF 的标签名落在哪个字段）没有一手答案前，PDF 的 `structured` 等级只能靠字号聚类猜测，而 §4.0 已经把「猜出来的标题」降级为 `inferred`。

**未决项的优先次序建议：U3 先做。** 它成本最低（手写一份 `w:styles` 里 `w:name` 为「标题 1」的 docx 即可），而失败后果最重：中文 Word 文档整篇标题静默消失，产物读起来正常、检索能用、只有章节结构没了——正是 C1 与 `extract.ts` 模块文档点名的最坏情形。U1/U2/U8 是「PDF 能做到什么等级」，U3 是「会不会悄悄做错」。

### 10.2 由实验得到的四条实现要求（比 §4.2 的原假设更准）

1. **风险的真正触发条件是 styleId，不是显示语言。** 中文 Word 的内置样式 ID 仍是 `Heading1`，所以 §4.2「必须同时写中英 styleMap，否则标题静默消失」这条要更正：默认表已经覆盖「英文 styleId + 任意语言名字」。会漏的是**非 Word 生成器**把 heading 的 styleId 写成 `1`/`a1`/`_Heading1` 之类，同时 `w:name` 也不是英文规范名。D 就是这一类的最坏形态。
2. **`w:outlineLvl` 被 mammoth 完全忽略**（`grep -rn outlineLvl lib/` 零命中）。所以自定义名字、只靠「大纲级别」标标题的文档（Word 的「目录级别」正是这个）默认一律丢。补救必须由我们自己读 `word/styles.xml`。
3. **推导式 styleMap 实测有效，但选择器有两种语法陷阱**：
   - `p.<styleId>` 只在 styleId 是合法 CSS 标识符时可用；`p.1 => h1:fresh` 被解析器拒了，报 `Expected identifier but got integer "1"`，条目**静默丢弃**；
   - `p[style-name=…]` 只认单引号，写成双引号报 `Expected string but got unrecognisedCharacter`；
   - 两种失败都只进 `result.messages`，不抛异常。
   因此推导函数要按 styleId 形状二选一，并且**必须把 `result.messages` 里的 `Did not understand this style mapping` 与 `Unrecognised paragraph style` 当成失败来断言**——这正是 D 类文档唯一的可见信号（实测文案：`Unrecognised paragraph style: '标题 1' (Style ID: 1)`）。
4. **不要依赖自定义条目与默认条目的优先级。** 实测不一致：同种选择器时默认条目赢（自定义 `p.Heading2 => h1` 对 `w:outlineLvl=1` 的文档，产物仍是 `<h2>`），异种选择器时自定义赢（自定义 `p.a1 => h3` 压过默认的 `p[style-name='Heading 1'] => h1`）。结论是**关默认、自带全量映射**（选项名是 `includeDefaultStyleMap: false`，不是 `useDefaultStyleMap`——后者被 mammoth 忽略且不报错）。已验证关默认 + 只给推导映射在真机文件上仍得 62 个标题、产物字节数与开默认时相同（35 185 字符），即推导映射完整覆盖了 Word 规范结构。

### 10.3 因此推荐的 DOCX 解析形态

先读一次 `word/styles.xml`，对每个 `w:type="paragraph"` 样式求层级：`w:outlineLvl` 存在即 `level = val + 1`，
否则用名字模式 `(标题|heading|見出し…)\s*([1-6])` 兜底；命中 1–6 就产一条映射，styleId 合法作 CSS 标识符时用
`p.<styleId> => h<n>:fresh`，否则用 `p[style-name='<name>'] => h<n>:fresh`（名字含 `'` 时要按 mammoth 语法处理或退回 class 形式）。
调用 `mammoth.convertToHtml({buffer}, {styleMap, includeDefaultStyleMap: false, includeEmbeddedStyleMap: false})`。
产物判据仍走 §1.2，并把 `messages` 里的两类告警计入 `structure` 降级依据。
名字模式表要留在配置里（哪些语言算标题名是产品决定，不是解析器决定），默认至少含中英两种。

### 10.4 仍未定论的部分

**「中文版 Word 实际写出什么样的 styles.xml」这一步没被本次实验覆盖**，因为手头没有 Word 真机产物：
本仓库的 docx 是 html→docx 流水线生成的，只能证明规范结构安全。要闭合，需要一份用户真实用 Word（简体中文）保存的
带多级标题的 docx，检查其 `w:styleId`/`w:name`/`w:outlineLvl` 三元组——这是 §7 U3 剩下的那半。
按 §10.2 第 1 条，这一步的风险已从「所有中文文档都丢标题」下调为「非 Word 生成器 + 非规范 styleId 的文档丢标题」，
而推导式映射对两种情形都成立，所以它不再阻塞阶段 2 的开工。

顺带否证了 §4.2 的另一句：base64 内联图片的风险在真机文件上未复现（该文件无图片，故既未证实也未否证），
`convertImage` 的正确签名留到阶段 2 用含图 fixture 再定。

## 11 U2 实验记录（2026-09-21，主体定论，一格待补）

### 11.1 真机中文 PDF：两个引擎结果一致

用机器上现成的四份中文 PDF（Pandoc/LaTeX 与截图导出产物，非本仓库文件）：

| 文件 | 页数 | unpdf 非空白字符 | pdfjs 非空白字符 | 汉字数（unpdf 全文） |
|---|---|---|---|---|
| `AI-Agents-in-Depth-zh-CN.pdf` | 316 | 467 633（全文，5.0 s） | 11 909（仅前 6 页，0.73 s） | 300 108 |
| `bits_cn.pdf` | 3 | 2 096 | 2 096 | 162 |
| `bpftrace_cn.pdf` | 4 | 2 812 | 2 812 | 545 |
| `hermes_cli_cheat_sheet_cn.pdf` | 2 | 10 189 | 10 189 | 1 696 |

三份小文件**字符数完全相等**（第四份是取页范围不同，不可比）。中文未乱码、未丢字。
316 页中文书全文抽取 5.0 s，量级上完全落在 §5.4 的构建预算内。

### 11.2 为什么这四份不需要 cmaps：它们都内嵌了字体

解开对象流后统计（`/FontFile2|/FontFile3`、`/Encoding /Uni…`、`CIDSystemInfo`）：

| 文件 | Type0 字体 | 嵌入字体程序 | 预定义 Adobe CMap | CIDSystemInfo Ordering |
|---|---|---|---|---|
| `AI-Agents-in-Depth-zh-CN.pdf` | 512 | 791 | 无 | `Identity` / `UCS` |
| `bits_cn.pdf` | 8 | 8 | 无 | `Identity` / `UCS` |
| `hermes_cli_cheat_sheet_cn.pdf` | 3 | 3 | 无 | `Identity` / `UCS` |

BaseFont 全是子集前缀形式（`TLEZMK+PingFangSC-Regular`、`YNJEGF+LxgwWenKaiGB-Bold`、`ZJOFUI+LMRoman12-Bold-Identity-H`）。
即：**现代工具链产出的中文 PDF 走的是"内嵌子集 + Identity/UCS"路线，不需要 Adobe CMap 表**。
需要 cmaps 的是另一类：引用系统字体且用 `/UniGB-UCS2-H` 之类预定义 CMap 编码、字体程序未内嵌的 PDF。

### 11.3 结论：unpdf 的缺口只是数据文件，不是代码路径

对 `unpdf/dist` 的三个代码文件（合计 1.63 MB）做字面量统计：
`cMapUrl` 出现 15 次、`cMapPacked` 9 次、`standardFontDataUrl` 17 次、`bcmap` 5 次、`UniGB` 8 次；
而 `unpdf` 的类型声明里 `getDocumentProxy(data, options?: DocumentInitParameters)` 直接接受这些参数。
所以 unpdf **保留了 CMap 读取代码，只是不随包分发 `.bcmap` 数据文件**。
配合实测的目录体量，PDF 通道的体量选择因此是：

| 方案 | 体积 | 覆盖 |
|---|---|---|
| `unpdf` 单包 | 2.4 MB | 内嵌字体的中文 PDF（§11.1 四份全部命中） |
| `unpdf` + 自备 `cmaps/` | 2.4 MB + 1.5 MB | 再加"预定义 CMap + 字体未内嵌"一类 |
| `pdfjs-dist` 整包 | 35 MB（其中 `build/` 12 MB、`cmaps/` 1.5 MB、`standard_fonts/` 0.82 MB、共 554 文件） | 同上 + 官方支持的其余参数 |

因此 §7 U2 里「若可，用 2.1 MB 换掉 33 MB」的前提成立，且比原设想更好：`cmaps` 实测 169 个条目 / 1.5 MB
（§2.1 里的「107 个文件」是按 jsDelivr 清单数的，本机安装目录实测为 169，以本机为准）。
`cmaps` 内容源自 Adobe 的 Unicode CMap 包，搬运它的许可义务要在阶段 3 之前单独核（`node_modules/pdfjs-dist/cmaps/LICENSE`）。

### 11.4 没被证到的那一格，以及两个必须记下来的假阴性陷阱

**未证到**：`unpdf` + 自备 `cmaps/` 端到端解出一份"字体未内嵌 + 预定义 CMap"的 PDF。
我尝试手写 Type0/`UniGB-UCS2-H` 的最小 PDF 作 fixture，两个引擎都返回空文本、pdfjs 另有
`FormatError: Illegal character: 41`，且**同一份骨架连拉丁对照组（Helvetica/WinAnsi）也取不到文本**——
说明是 fixture 自身不合法，不是解析器的能力差异，这条结论因此不能用推断补齐。
补法：用真机 Word（选「不嵌入字体」）或 LibreOffice 导出一份，或从公开可再分发语料取一份，
再跑 `unpdf` 带/不带 `cMapUrl` 两种。风险评级：内嵌字体是主流（§11.2 三份全中），这一格属于长尾。

**陷阱一（会让门禁假绿）**：`GlobalWorkerOptions.workerSrc` 给成 Windows 路径（`E:\…` 或 `E:/…`）时，
pdfjs 报 `Setting up fake worker failed: Only URLs with a scheme in: file, data, and node are supported`，
随后**不抛异常、静默返回空文本**。必须给 `file://` URL（`pathToFileURL(...).href`）。
这条最阴险的地方在于：一个断言「产物非空」的门禁会红，而一个只断言「调用不抛错」的门禁会绿。

**陷阱二**：`cMapUrl` / `standardFontDataUrl` 要的是**正斜杠绝对路径带尾斜杠**；
给 `file://` 形式会被自己的 factory 校验拒绝（`Invalid factory url: "file:///…"`）。
即 workerSrc 与 cMapUrl 在 Windows 上要求**两种不同**的路径形态，写成一个 helper 会必错一边。

**陷阱三**：同一进程里同时 `require`/`import` unpdf 内置的 pdfjs 与外部 pdfjs-dist 时，worker 版本会打架
（实测 `The API version "6.3.289" does not match the Worker version "6.1.200"`）。
两个引擎的对照实验必须分进程跑，插件里也不该同时装两份 pdfjs。
