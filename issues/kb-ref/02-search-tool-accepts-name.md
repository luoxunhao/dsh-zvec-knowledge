# KB-REF-02 — 检索工具的 collection 参数接受名称与标识

**What to build（要构建什么）：** 用户手打 `@知识库名` 提问时，检索**一次成功**，不再先失败一次去换清单。端到端可见行为，不是分层实现列表。

**Blocked by:** KB-REF-01（解析纯函数与其门禁）。

**Status:** ready-for-agent

## 背景

客户端菜单选中会插入 chip，chip 提交时序列化成含正确标识的句子。但当用户**手打** `@名称` 时，模型拿到的是显示名，于是把显示名当标识传参，检索报「集合标识非法」，再靠 `discovery_needed` 那次额外往返才拿到清单。每次对话都要多烧一次往返，且首调必然失败。

`KB-REF-01` 已提供解析逻辑；本 issue 把它接进工具的真实调用路径。

## 范围

- 在检索工具中，当 `collection` **已给出**时，先用 `KB-REF-01` 的解析把输入翻译为标识，再进入后续检索。
- 解析所需的清单来自**既有的知识库发现通道**（宿主已有的列举能力），不新增通道。
- 失败语义与既有约定一致：**不抛异常**，返回可判定的失败结果与可读说明。
- 失败原因新增**歧义**一档，与既有「集合不存在」「空结果」等并列区分。
- **歧义**与**无匹配**的说明文本必须列出候选（标识 + 名称 + 是否已构建），使调用方下一次调用能自我纠正。
- **`collection` 省略时的既有发现分支保持不变** —— 包括「只有一个已构建知识库则直接检索它」这一行为，不得回归。

## 验收标准

- [ ] 手打显示名（`@agent-book` 场景）调用检索，**首次即成功**，不再返回「集合标识非法」。
- [ ] 手打裸标识调用检索，行为与改动前完全一致（零回归）。
- [ ] 粘贴整句序列化模板作为 collection，同样解析成功。
- [ ] 两个知识库同名时，返回歧义失败，说明中列出全部候选，且**不随意选中其中任何一个**。
- [ ] 输入无法匹配任何知识库时，返回无匹配失败，说明中列出当前全部可用知识库。
- [ ] `collection` 省略时仍走原发现分支：只有一个已构建知识库时直接检索它；多个时返回清单。
- [ ] 解析失败**不消耗**嵌入与检索预算（不产生向量请求）。
- [ ] 既有全量校验套件保持全绿。
- [ ] 新增校验脚本覆盖上述各分支，并随 `npm run verify` 运行。

## 证据要求

必须给出**真实调用**的证据：一条以显示名调用并成功的检索记录，而非仅单元测试通过。

## 不做

- 不更改 `query` / `collection` / `topk` 的参数名。
- 不更改 `match_score` 数值语义与分档边界。
- 不重写客户端触发源的注册链路（它工作正常）。
- 不改动已省略 collection 时的发现逻辑。
