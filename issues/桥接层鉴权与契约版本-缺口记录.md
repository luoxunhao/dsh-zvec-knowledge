## 1 事实与证据

四条，均取自基线提交的实际源码，不是推断。

1. **桥接路由不做 CORS 预检，也不校验 `Origin`。**
   `src/host/bridge.ts` 全文没有 `OPTIONS` 处理，不读写任何 `access-control-*` 头。
   唯一的响应头写入点是 `send()`（`:156-166`），它设 `content-type`、
   `cache-control: no-store`、`content-length` 三项。

2. **令牌只挡跨源页面，不挡本机进程。**
   源码在 `bridge.ts:28-33` 自陈：该路由对任何能连上 loopback 端口的进程都可达，
   与本服务上其他路由一致；并写明**有意**不做第二套鉴权，理由是"邻居路由本来就开着，
   单独立一套只会造成边界存在的错觉"。因此本条不是疏漏，是一个待裁决的设计立场。

3. **失败的状态码分两类，不是一类。**
   业务失败走 `200` + `{ ok: false, reason }`（`:548`、`:568`、`:613`、`:642`）；
   令牌缺失或不匹配走 `403` + `reason: 'unauthorized'`（`:519`、`:583`），
   且注释说明为何是 403 而不是 404——路由本身不是秘密，调试时"未授权"比"不存在"有用。

4. **契约没有版本字段。**
   `KbApiResponse`（`src/shared/contract.ts:144-153`）只有 `ok` / `result` / `error` / `reason`。
   全文件检索 `version` 与 `v:` 均无命中。

## 2 影响

- 任何本机进程可调用桥接层的**全部**方法，包括删除集合这类写操作。令牌不构成对该场景的防线。
- host 与 client 分别构建、分别部署。二者版本不匹配时，客户端无从判定对端是哪一版契约，
  只能从单个方法调用失败反推。

## 3 附带发现：一条指向不存在目标的指引

`bridge.ts:28-33` 把安全边界的说明交给 "the security note in the README"，
并引用 `{@link KB_API_PATH}`。但 `plugin/README.md` 中没有这一节：
`KB_API_PATH` 在该文件中出现 0 次，含"令牌"的 20 处全部指设计令牌（design tokens），
与桥接鉴权无关。读者顺着注释找安全边界会找不到落点。
